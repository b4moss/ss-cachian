# コンセプト

- サーバーサイドキャッシュの責務は、DBを本質的なアクセスのみにとどめ、守ることである。
- セッションをDBに保存する場合、それは本質的にDBの責務と言えるのか
  - Writeに関しては致し方ないが、セッション確認・維持のReadが頻繁に発生するのは考えもの
- DBクエリキャッシュも、必要最低限のReadにとどめるために必要
- 一方でインメモリキャッシュ・Redis/Valkey・Firestoreなど、複数のメモリストレージ種がある
- これらをAdapter/driver化するにと同時に複数のストレージを1つのアプリケーションで扱えるようにする
- さらに複数ストレージをL1, L2, L3と階層化して使い分けられるようにする
- キービルダー機能。バージョニングや、クエリ内容を組み立てられるようにする

# 機能ドメイン分類

## Driver

- インメモリ
- Redis / Valkey
- MongoDB
- Firestore
- ファイルシステム

## レベル機能

- L1miss -> L2 hit などの機能
- 何階層でも設計可能
- レベルごとにストレージを指定可能

## キャッシュタイプ定義

- キーの切り方
- TTL
- バリューの構造
- 指定ストレージ

を定義できるようにする

## 想定利用イメージ

### テナント共通レスポンス

例えば各階層を以下で定義する

- L1: インメモリ
- L2: Firestore

ロジックは以下

- DBアクセス、返却
- L1, L2キャッシュ保存
- 2度目のアクセス
- L1 hit -> 返却
- L1 miss -> L2 hit -> 返却
- L1 miss -> L2 miss -> DB 再Read

## パージやTTL切れ

- 明確なパージAPIは用意する
- TTL切れは、ストレージ側で任せられるものは任せる(Redis / Valkey等)
- そうでないものはTTLパージAPIを driver側で用意する
